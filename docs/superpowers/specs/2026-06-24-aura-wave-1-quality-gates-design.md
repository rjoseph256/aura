# Aura Wave 1 — Quality gates design

**Goal:** Put the CI safety net in place before the rest of Wave 1. After this
sub-project, the app target (and its embedded widget extension) compiles in CI on
every pull request, the whole codebase builds under Swift 6 language mode, and
SwiftLint enforces a tuned default rule set under `--strict`.

**Status:** approved design, ready to plan.

## Context

Wave 1 is the structural-foundations wave. It breaks into five independent
sub-projects, each shipped on its own through its own spec, plan, and build
cycle:

1. Quality gates (this document)
2. Design system
3. Ride-session coordinator
4. Persistence and schema migration
5. Navigation rebuild

The agreed build order leads with this sub-project so that every later refactor
lands behind a working CI gate. Three of the four remaining sub-projects touch
the app target, and the coordinator and navigation work is the most
concurrency-sensitive code in the app, so the gate has to exist first to be
worth anything.

Current state, confirmed against the code:

- `AuraCore/Package.swift` is `swift-tools-version: 5.10` with no concurrency
  flags and no language-mode setting.
- `.github/workflows/ci.yml` runs a single job that does `swift test` in the
  `AuraCore` package. It never compiles the app target, so a break in a Mapbox
  provider, a SwiftUI view, or the wiring passes CI green.
- There is no SwiftLint configuration anywhere in the repository.
- The app target has zero tests. All tests live below the app boundary in the
  pure package.
- The app reaches Mapbox through two tokens, neither committed: a public
  runtime token (`pk.…`) in `Aura/Resources/MapboxAccessToken` (gitignored,
  read at launch by `AuraApp.configureMapbox()`), and a secret `Downloads:Read`
  token in `~/.netrc` that Swift Package Manager needs to download the Mapbox
  binary SDK from `api.mapbox.com`. CI has no GitHub Actions secrets today.
- The project is generated by XcodeGen from `Aura/project.yml` and is not
  checked in. XcodeGen is installed locally but not on the CI runner.
- `Aura/project.yml` defines a fourth compiled target beyond the package and the
  app: `AuraWidgets`, an `app-extension` that hosts the Live Activity and Dynamic
  Island. Its Swift sources live in `Aura/Widgets/`, and it compiles two shared
  files by membership (`Aura/Sources/LiveActivity/RideActivityAttributes.swift`
  and `Aura/Sources/Theme/AuraTheme.swift`). It depends only on AuraCore and
  AuraKit, not Mapbox. The app target embeds it as a dependency, so building the
  `Aura` scheme also builds the extension.

## Decisions

Three decisions set the scope, each confirmed with the user:

1. **App-target build gate runs in real CI.** The user adds the two Mapbox
   tokens as repository secrets so the workflow can compile the app with
   `xcodebuild`. This is the strongest available gate and the core value of the
   sub-project.
2. **Swift 6 language mode across all four compiled targets** (AuraCore, then
   AuraKit, then the app and its `AuraWidgets` extension), enabled now rather than
   deferred, so the refactors that follow are checked from day one.
3. **SwiftLint with a tuned default rule set, green under `--strict`.** Fix
   violations now rather than carry a baseline. Run a standalone SwiftLint binary
   in CI rather than the SPM build-tool plugin.

## Pillar 1: Swift 6 language mode in dependency order

The rollout follows the dependency graph so each layer is clean before the next
depends on it. Each step is verified by a real build and the existing test suite
before moving on.

### AuraCore (pure logic library)

Bump `AuraCore/Package.swift` to `swift-tools-version: 6.0` and enable Swift 6
language mode for the package with `swiftLanguageModes: [.v6]` (or per target via
`swiftSettings: [.swiftLanguageMode(.v6)]`). Keep the library actor-agnostic: do
not set default MainActor isolation. AuraCore is already written to a Swift 6
standard and holds only value types and protocols, so this step should produce
little or no churn.

### AuraKit (depends on AuraCore)

Same Swift 6 language mode. AuraKit holds the `@MainActor @Observable` stores and
view models plus `LocationService`, and it already annotates main-actor isolation
explicitly where it belongs. Keep the module actor-agnostic at the default level
so the non-UI seams (`RideRecorder`, the mappers, the formatters) stay off the
main actor. Fix any `Sendable` gaps the compiler surfaces with the smallest safe
change: prefer immutable value types and isolated annotations over
`@unchecked Sendable`.

### App (Aura, SwiftUI plus Mapbox)

Set `SWIFT_VERSION = 6.0` in `Aura/project.yml`. Because the app is almost
entirely UI-bound, also adopt the Swift 6.2 executable posture: enable
Approachable Concurrency and set Default Actor Isolation to `MainActor`. With
default MainActor isolation, unannotated app code is inferred as `@MainActor`,
which removes most of the annotation and `Sendable` friction that Swift 6 mode
would otherwise create in a SwiftUI and Mapbox codebase. The exact XcodeGen
build-setting keys (for example `SWIFT_VERSION`, `SWIFT_DEFAULT_ACTOR_ISOLATION`,
and the Approachable Concurrency setting) are verified against the installed
toolchain during implementation, with the upcoming-feature flag form in
`OTHER_SWIFT_FLAGS` as the fallback if a dedicated setting is unavailable.

Where Mapbox SDK types still fail `Sendable` checks across an isolation boundary,
use `@preconcurrency import MapboxMaps` (and the other Mapbox modules as needed),
documented with the intent to remove it when the SDK catches up. Do not reach for
`nonisolated(unsafe)` or `@unchecked Sendable` to silence Mapbox diagnostics.

Risk note: the app migration is the one unknown here. If approachable concurrency
plus `@preconcurrency` do not resolve a diagnostic cleanly, apply the smallest
safe fix from the concurrency triage (annotate the isolation, snapshot an
immutable value, mark a conformance isolated) and record anything that needs a
follow-up.

### AuraWidgets (Live Activity extension)

The widget extension is its own Xcode target with its own settings block in
`Aura/project.yml`, so it needs the language-mode settings applied to it directly,
not just to the app. Set `SWIFT_VERSION = 6.0` and the same executable posture
(Approachable Concurrency and Default Actor Isolation set to `MainActor`) on the
`AuraWidgets` target. WidgetKit and ActivityKit code is UI-bound, so the same
inferred main-actor isolation that helps the app helps here. The extension does
not import Mapbox, so it should not need `@preconcurrency`. The two files it shares
with the app by membership (`RideActivityAttributes.swift` and `AuraTheme.swift`)
compile into both targets, so they must satisfy whichever posture is stricter;
both are small (a value-type `ActivityAttributes` contract and a color and font
theme) and are expected to need no change.

## Pillar 2: App-target build gate in CI

Add an `app-build` job that compiles the app on every pull request and on push to
`main`. It runs on a macOS runner with the latest stable Xcode. Steps:

1. Check out the repository.
2. Install XcodeGen (`brew install xcodegen`).
3. Reconstruct Mapbox authentication from secrets:
   - Write `~/.netrc` (mode `600`) with the secret download token:
     ```
     machine api.mapbox.com
       login mapbox
       password ${MAPBOX_DOWNLOADS_TOKEN}
     ```
   - Write `Aura/Resources/MapboxAccessToken` containing the public token from
     `${MAPBOX_PUBLIC_TOKEN}` on a single line, so the bundled resource exists at
     build time.
4. Generate the project with `xcodegen generate`.
5. Build with `xcodebuild build -scheme Aura` against a generic iOS Simulator
   destination (`-destination 'generic/platform=iOS Simulator'`, which does not
   depend on a specific simulator runtime being present), with
   `CODE_SIGNING_ALLOWED=NO`. Building the `Aura` scheme also builds the embedded
   `AuraWidgets` extension, so the one build step is the compile gate for both the
   app and the widget. Name the scheme explicitly so this coverage is intentional.

The two required repository secrets are:

- `MAPBOX_DOWNLOADS_TOKEN` — the secret token with `Downloads:Read` scope. This
  is the `sk.…` value that `.mapbox-setup.md` documents as the `~/.netrc`
  password; the spec uses the descriptive name, but it is the same token.
- `MAPBOX_PUBLIC_TOKEN` — the public `pk.…` runtime token.

The implementation hands the user the exact `gh secret set` commands. Until both
secrets exist, the `app-build` job fails; the other jobs are unaffected.

This is a compile gate only. The app has no tests today and writing them is out
of scope here (it belongs with the Wave 2 cockpit work), so the job uses `build`,
not `build-for-testing`.

## Pillar 3: SwiftLint

### Configuration

Add `.swiftlint.yml` at the repository root, starting from the SwiftLint default
rules. Use `disabled_rules` and per-rule tuning only for rules that genuinely
clash with the established conventions in this codebase, with an inline comment on
each explaining why. Set `included` to `AuraCore/Sources`, `AuraCore/Tests`,
`Aura/Sources`, and `Aura/Widgets` (so the widget extension code is linted too),
and `excluded` to `.build`, `DerivedData`, `docs`, and any generated output. Add a
relaxed child `.swiftlint.yml` under `AuraCore/Tests` for
test-only tolerances (for example allowing `force_try` and `force_unwrapping` in
test code) rather than excluding tests from linting.

### One-time cleanup

Run `swiftlint --fix` for the autocorrectable rules and commit that as its own
reviewed change, separate from any hand edits. Then fix the remaining violations
by hand until the repository is clean. Do not adopt a baseline: the decision is to
fix now, not defer.

### CI and local use

Add a `lint` job that runs `swiftlint --strict` so any violation, warning or
error, fails the build. Pin the SwiftLint version rather than taking whatever
`brew install` happens to provide, so the rule set does not drift underneath the
repository between runs; pick a SwiftLint version compatible with the Xcode 26 /
Swift 6.2 toolchain. Add a `scripts/lint.sh` convenience that runs the same
invocation locally.

This follows the user's choice of a standalone binary over the SPM build-tool
plugin, which would run on every Xcode build and slow local iteration. The
trade-off is that the version must be pinned explicitly, which the CI step and the
local script both do.

## CI structure

Extend the existing `.github/workflows/ci.yml` into three jobs that run in
parallel:

- `package-tests` — the current job, `swift test` in `AuraCore`, now exercising
  the package under Swift 6 language mode. Keep its existing macOS runner and
  Xcode setup.
- `app-build` — the new app compile gate described above.
- `lint` — the new SwiftLint job.

Parallel jobs keep the wall-clock short and make a failure point at the thing that
broke. The alternative of folding the app build into the package job would use one
fewer macOS runner at the cost of a slower, less legible pipeline; the parallel
layout is the chosen design.

## Out of scope

- Writing app-target tests. The app stays a compile gate here; test authorship is
  later work.
- The SPM build-tool plugin for SwiftLint.
- A SwiftLint baseline.
- Any of the other four Wave 1 sub-projects.
- Behavior changes. Every edit in this sub-project is configuration or a
  mechanical, behavior-preserving fix.

## Testing and verification

- The `AuraCore` and `AuraKit` test suites stay green after the Swift 6 mode
  flip; this is the proof that the package migration changed no behavior.
- `xcodegen generate` followed by `xcodebuild build` succeeds locally (confirmed
  through the build-tools agent) and in CI.
- `swiftlint --strict` exits clean locally and in CI.
- No flagship runtime behavior is touched, so no device or simulator
  re-verification of recording or navigation is required for this sub-project.

## Risks and mitigations

- **App-target Swift 6 plus Mapbox `Sendable` friction.** Mitigated by adopting
  approachable concurrency and default MainActor isolation on the app and by
  `@preconcurrency import` for Mapbox. If a diagnostic resists, fall back to the
  smallest safe isolation fix, never to unsafe escapes.
- **The app-build job fails until secrets are added.** Expected and bounded: the
  workflow lands with the secret names called out and the exact commands handed to
  the user, and the other jobs are independent.
- **SwiftLint cleanup touches many files.** Kept mechanical and
  behavior-preserving, with the autocorrect pass committed separately from the
  hand fixes and from the concurrency work, so each change set stays reviewable.
- **A floating SwiftLint version changes rules under the repository.** Mitigated
  by pinning the version in CI and in the local script.

## Rollout order

The implementation plan sequences the work so each change set is small and
independently verifiable:

1. SwiftLint configuration plus the one-time cleanup (mechanical, no behavior
   change, lands the repo lint-clean first).
2. Swift 6 language mode for AuraCore, verified by `swift test`.
3. Swift 6 language mode for AuraKit, verified by `swift test`.
4. Swift 6 mode plus approachable concurrency and default MainActor isolation for
   the app and the `AuraWidgets` extension, verified by a local
   `xcodebuild build -scheme Aura` (which compiles both).
5. CI wiring: the `app-build` and `lint` jobs added to the workflow, the
   `package-tests` job confirmed still green.
