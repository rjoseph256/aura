# Onboarding a collaborator

How to get Aura building, running, and testing on a second person's Mac. Written for
the case where **one person owns the Apple Developer account** and adds the collaborator
to their team, rather than everyone holding their own paid membership.

Two things are gated and not in the repo: **Mapbox tokens** and **Apple code signing**. The
code itself is public and the Supabase backend needs no credentials, so those come for free.
Contributing back needs a little more (GitHub push access and Linear), covered in
[§6](#6-repo-linear-and-backend-access). Work top to bottom.

## 1. Base toolchain

On the collaborator's Mac:

- **Xcode 26.x** (App Store). Not 16: the app target builds in Swift 6 language mode with
  `SWIFT_DEFAULT_ACTOR_ISOLATION: MainActor` and uses iOS 26 APIs, none of which Xcode 16
  can compile. Once it is installed, point the command line at it and accept the license:

      sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
      sudo xcodebuild -license accept
      xcodebuild -runFirstLaunch

- **The iOS simulator runtime**, which Xcode 26 downloads separately from the app. A fresh
  install has no iPhone simulator at all. Check, and install it if the list comes back empty:

      xcrun simctl list devices available | grep iPhone
      xcodebuild -downloadPlatform iOS      # only if the check found nothing

  Skipping this produces `unable to find destination matching...` on the first build, which
  reads like a wrong device name rather than a missing runtime.

- **Homebrew**, then `brew install xcodegen gh`.

- **SwiftLint 0.64.1 specifically**, which is the version CI runs `--strict` against. Do not
  use `brew install swiftlint`: it installs whatever is current, newer releases add rules, and
  the result is lint that passes locally and fails CI (or the reverse). Use the same pinned
  build CI does:

      mkdir -p ~/bin
      curl -fsSL -o /tmp/swiftlint.zip \
        https://github.com/realm/SwiftLint/releases/download/0.64.1/portable_swiftlint.zip
      unzip -oq /tmp/swiftlint.zip -d /tmp/swiftlint
      mv /tmp/swiftlint/swiftlint ~/bin/
      echo 'export PATH="$HOME/bin:$PATH"' >> ~/.zprofile

- Clone the repo. It is public, so this needs no access grant (pushing does: see
  [§6](#6-repo-linear-and-backend-access)). The Xcode project is *not* checked in, it is
  generated by XcodeGen from `Aura/project.yml`. So the loop is always:

      cd Aura
      xcodegen generate      # regenerates Aura.xcodeproj (gitignored)

  Run this after every clone, after every branch switch, and after any `project.yml` change,
  then open `Aura/Aura.xcodeproj`. Forgetting it is worth recognizing on sight: a stale project
  is missing whatever files the branch added, and the build fails with `cannot find X in scope`
  plus a cascade of type-inference errors in files you did not touch. That looks like broken
  code and is actually a stale project.

### A note on Xcode versions ahead of the project

The project is validated against **Xcode 26.3 (Swift 6.2.4)**, which is what CI pins and what
the owner develops on. A newer Xcode is not automatically safe: Swift 6.3 tightened region
isolation and rejects code that 6.2 accepts, which is exactly how ROH-116 was found (two
ActivityKit calls that had been on `main`, green, for months).

If you are on a newer Xcode and hit a concurrency error nobody else sees, that is the likely
shape of it. Report it rather than working around it locally, and do not turn off
`SWIFT_APPROACHABLE_CONCURRENCY` to make it go away. CI has a `Toolchain canary` job on Xcode
26.6 for this, so it should now be caught before you are.

## 2. Mapbox tokens (each person needs their own — both gitignored)

Aura uses two Mapbox tokens, neither committed:

- **Public runtime** `pk.…` → `Aura/Resources/MapboxAccessToken` (a plain text file holding
  only the token). Bundled into the app; read at launch by `AuraApp.configureMapbox()`.

      echo 'pk.your_public_token' > Aura/Resources/MapboxAccessToken

- **Secret download** `sk.…` with the `Downloads:Read` scope → `~/.netrc`. Swift Package
  Manager needs this to pull the Mapbox binary SDK from `api.mapbox.com`.

      machine api.mapbox.com
        login mapbox
        password sk.your_download_token

  Then `chmod 600 ~/.netrc`. A world-readable `.netrc` is ignored rather than rejected, so
  the wrong permissions surface later as an unexplained 401 during package resolution.

Cleanest approach: **invite the collaborator to the Mapbox account** (Mapbox dashboard →
invite member) and have them mint their own `pk`/`sk` tokens, rather than sharing the
owner's secret `sk`. Full detail and token scopes are in [.mapbox-setup.md](../.mapbox-setup.md).

The first `xcodegen generate` + build is slow while SPM downloads the SDK. A 401/403 there
means the `~/.netrc` token is missing or lacks `Downloads:Read`.

## 3. Supabase — nothing to configure ✅

The Supabase URL and publishable key are hardcoded in
`Aura/Sources/Sync/SupabaseClientProvider.swift` and are public-safe by design (the key is
RLS-gated). The collaborator's build points at the shared cloud project out of the box — no
credentials, no env files. Managing the backend itself (edge functions, migrations) stays
with the account owner.

## 4. Apple signing — add the collaborator to your team

The project commits the signing config so it survives `xcodegen generate`:

- Team `DEVELOPMENT_TEAM: C3LFTV2QYK`, automatic signing.
- Bundle IDs `com.rohunjoseph.aura` and `com.rohunjoseph.aura.AuraWidgets`.

Because the team is committed, the collaborator does **not** edit any project files. They
just need to be a member of that team:

1. **Owner:** App Store Connect → **Users and Access** → invite the collaborator's Apple ID
   (role **Developer** or **Admin**). Included in the existing paid membership — extra team
   members cost nothing.
2. **Collaborator:** Xcode → Settings → Accounts → sign in with that Apple ID. Their account
   now shows team `C3LFTV2QYK`.
3. Open the project, and let Xcode manage signing for both the app and the `AuraWidgets`
   extension. Automatic signing issues provisioning for the shared bundle IDs and
   capabilities (Sign in with Apple, HealthKit, App Groups `group.app.aura.ios`,
   iCloud/CloudKit `iCloud.com.rohunjoseph.aura`, Background Modes) — no per-person changes.

### Registering the device (Silver Bar)

The collaborator's iPhone is **Silver Bar**, the second-identity device from the group-ride
two-device matrix. To run on it:

1. Plug it into their Mac, select it as the run destination in Xcode, and Run. With the
   collaborator on the team, Xcode registers the device UDID and builds a profile
   automatically on first Run.
2. If it was ever registered under the owner's account before, no action is needed — it
   already counts against the team's device list.

For a second live identity (group rides need two Apple IDs on two phones), Silver Bar signs
in as rider 2 while the owner's phone is rider 1. See [DEVICE-TESTING.md](DEVICE-TESTING.md).

## 5. What runs where

- **iOS Simulator** — no signing needed at all; the fastest path for everyday feature work.
  Most of the app runs here.

      cd Aura
      xcodebuild -scheme Aura -destination 'platform=iOS Simulator,name=iPhone 17' build

- **Silver Bar (device)** — required for the checks the simulator can't prove: locked-screen
  background recording, turn haptics and arrival, Live Activity / Dynamic Island, Home and
  Lock Screen widgets, HealthKit, and the two-device group-ride and iCloud matrices. The full
  device checklist is [DEVICE-TESTING.md](DEVICE-TESTING.md).

- **Pure-logic tests** run without any of the above:

      cd AuraCore && swift test --no-parallel

  CI runs the same on every push (`.github/workflows/ci.yml`).

## 6. Repo, Linear, and backend access

The Apple team invite in [§4](#4-apple-signing--add-the-collaborator-to-your-team) covers
building and running. Three other things gate actually contributing, and none of them announce
themselves until the collaborator is blocked.

**GitHub push access.** The repo is public, so cloning, building, and reading all work with no
grant at all. That hides the gap: the first `git push` is where it surfaces. If they will open
PRs, add them under Settings → Collaborators on `rjoseph256/aura` during setup, not when they
are already blocked.

**Linear.** Development runs through the board (see [BOARD.md](BOARD.md)), so a collaborator
needs a workspace invite: linear.app/rohun → Settings → Administration → Members → Invite
people. Use role **Member**, not Guest. Guests are scoped to explicitly shared teams and cannot
see workspace-level Projects, which is where the epics live.

Worth knowing separately: a Linear invite does not give their *Claude Code* access to Linear.
The MCP connector is per-user OAuth, so they authorize it themselves in their claude.ai
connector settings, or with `/mcp` in an interactive terminal. Until they do, their sessions
cannot move issues, and keeping the board honest is part of the flow rather than optional.

**Supabase.** Nothing is needed to build or run. The project URL and publishable key are
hardcoded in `Aura/Sources/Sync/SupabaseClientProvider.swift` and are public-safe by design,
so a collaborator's build talks to the shared cloud project out of the box. They only need an
org invite if they are going to write migrations or deploy edge functions. Keep it with the
account owner until that is actually the work.

## If they are mostly a tester, not a developer

Skip the laptop setup entirely: add their Apple ID under **Users and Access** and distribute
builds through **TestFlight** (internal testing). They install on Silver Bar with no Xcode,
no tokens, and no signing. Best when the goal is "try builds and report bugs" rather than
"write code."

## Quick checklist

Order matters at the top: the two slowest items are downloads, and the two invites are
asynchronous, so start all four before anything else.

- [ ] Xcode 26.x from the App Store, then `xcode-select`, license, `-runFirstLaunch`
- [ ] Owner invites collaborator in App Store Connect → Users and Access (role Developer)
- [ ] Owner adds them under GitHub → Settings → Collaborators, if they will push
- [ ] Owner invites them to Linear as a Member
- [ ] iOS simulator runtime: `xcrun simctl list devices available | grep iPhone`, else
      `xcodebuild -downloadPlatform iOS`
- [ ] Homebrew, `brew install xcodegen gh`, SwiftLint pinned to 0.64.1 (not Homebrew's)
- [ ] Clone repo; `cd Aura && xcodegen generate`
- [ ] Mapbox `pk.…` → `Aura/Resources/MapboxAccessToken`
- [ ] Mapbox `sk.…` (`Downloads:Read`) → `~/.netrc`, mode 600
- [ ] Collaborator signs into Xcode with that Apple ID; team `C3LFTV2QYK` appears
- [ ] Collaborator authorizes the Linear MCP connector in their own Claude Code
- [ ] Build to Simulator (no signing) or Run on Silver Bar (auto-registers)
- [ ] `cd AuraCore && swift test --no-parallel` passes
- [ ] `swiftlint lint --strict` clean

## Once they are building

Setting up the machine is half of it. [COLLABORATOR-TASKS.md](COLLABORATOR-TASKS.md) covers the
other half: which board issues one person can actually finish without the owner's second phone
or Supabase access, how to reproduce Aura's development process (the superpowers pipeline, the

daily briefing of issues they can pick up unassisted.
