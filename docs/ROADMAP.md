# Aura roadmap

Aura is an iOS cycling app: plan a route to somewhere, get turn-by-turn voice
navigation, or just start a free ride and record the track. This file records what
is built, what the 2026-06-24 audit found, and the order we will build in next.

## Shipped

### Foundation and architecture

The code is split into three layers so the routing and navigation engines can be
swapped without touching the UI:

- `AuraCore` is pure Swift with no UIKit, SwiftUI, or Mapbox. It holds the models
  (`Ride`, `Route`, `Place`, `RideStats`), the stats and ranking logic, and the
  protocols that define the seams (`RoutingProvider`, `ElevationProvider`,
  `GuidanceSession`).
- `AuraKit` depends only on `AuraCore`. It has the observable view models and stores
  (`RideRecorder`, `RideStore`, `SettingsStore`), formatting, and the pure plotting
  helpers behind the thumbnails and sparklines. Location streaming
  (`LiveLocationProvider`, `SimulatedLocationProvider`) is confined to the main actor,
  so the CoreLocation callback and the async stream no longer race for the continuation.
- `Aura` is the app target: SwiftUI views plus the Mapbox-backed implementations of
  the `AuraCore` protocols.

The Xcode project is generated by XcodeGen and is not checked in. Tests run on the
`AuraCore` package and in CI on every push.

### Features

- Free ride and navigate-to-destination modes, both recording a GPS track and live
  stats (distance, moving time, speed, elevation gain).
- Turn-by-turn navigation with spoken instructions, built on Mapbox Navigation v3.
  The guidance lives behind a `GuidanceSession` protocol, so the turn card is driven
  by a plain event stream that a scripted double can replay in tests.
- Route planning returns up to three labeled options (Most paths, Fastest, Flattest)
  from Mapbox Directions. Real elevation comes from decoding Mapbox Terrain-RGB
  tiles, so "Flattest" is ranked on actual climb rather than a guess. "Most paths"
  goes to the most rideable option: a forced-dismount (walking) segment now counts
  against a route instead of for it. The route preview formats its stats with the
  shared `RideStatsFormatter`, so it honors the distance-units setting like the rest
  of the app.
- Persistence with SwiftData, a History list, and a Settings screen (units, voice,
  map style, offline Pittsburgh map download, weekly distance goal).
- A home dashboard: a weekly goal ring, a last-ride card, and a recents list that
  now survives relaunch.
- Route thumbnails in History and on the dashboard (drawn as a Canvas polyline, not
  a live map per row), and a per-route elevation sparkline in the route preview.
- Type scales with Dynamic Type across every screen: semantic text styles for labels
  and headings, and `@ScaledMetric` for the glanceable HUD and ring numerals, which
  stay inside their bounds at accessibility sizes. The ride HUDs and route preview
  clear the status bar with the safe area rather than a fixed inset.
- A Live Activity and Dynamic Island for an in-progress ride. A free ride shows elapsed
  time, distance, and speed; a navigated ride leads with the next turn (distance and
  instruction) over a quiet elapsed/distance row, with the turn distance turning green as
  the maneuver nears. It ships as the `AuraWidgets` WidgetKit extension, which shares the
  `RideActivityAttributes` contract and `AuraTheme` with the app by target membership —
  ActivityKit stays out of the SwiftPM package so CI's macOS `swift test` still builds. A
  `RideLiveActivityController` called from both ride HUDs owns start/update/end, guarded on
  `ActivityAuthorizationInfo`; elapsed time ticks on-device, so updates push only when the
  stats or the next turn change. It was wired straight from the HUDs ahead of the Wave 1
  ride-session coordinator, and needs no App Group — the content state carries the data.

## What the audit found (2026-06-24)

A skill-driven audit (Swift concurrency, SwiftUI, SwiftData, CoreLocation/Mapbox,
accessibility, and design) went through the whole codebase. The short version: the
architecture is genuinely good, the pure layer is well tested, and the taste is real.
The gaps are in the last mile of the platform work, where the app meets CoreLocation,
the navigation stack, the data store, and the system extensions.

**The one finding that matters most: a rider cannot lock the phone and keep recording
today.** This is the flagship behavior of a cycling app and it is not wired end to end.
`LiveLocationProvider` sets `allowsBackgroundLocationUpdates = true` and the Info.plist
declares the `location` background mode, but there is no entitlements file anywhere in
the project and no Background Modes capability, so the flag has nothing behind it. Only
`requestWhenInUseAuthorization()` is ever called; the "Always" usage string in the
Info.plist is present but dead. Nothing ever sets `isIdleTimerDisabled`, so the screen
auto-locks mid-ride and the app suspends before background location would even apply.
The track gets a hole. Fixing this is correctness work, not a feature, and it comes first.

The rest of the audit groups into a few themes.

- **Navigation is a hand-rolled `switch`, not a stack.** `AppRouter.screen` is an enum
  rendered by a top-level `switch` in `RootView`, with no `NavigationStack`, no typed
  path, and no `.navigationDestination`. It works for today's three linear screens, but
  it has no back-swipe, it tears down and rebuilds the Mapbox map on every transition,
  and it cannot represent a deep link into a ride. The planned group-ride and deep-link
  futures both need the appendable path this design does not have. This is the largest
  rebuild item and it unblocks several others.
- **The SwiftData schema will fight the first feature that touches it.** `RideRecord`
  carries `@Attribute(.unique)` on `id`, which is a hard incompatibility with the iCloud
  sync the spec wants. The full GPS track is a JSON `Data` blob stored inline in the row
  with no `@Attribute(.externalStorage)`, so the History list decodes roughly a megabyte
  per multi-hour ride just to show a date and a distance. There is no `VersionedSchema`
  or migration plan, so the first non-additive change risks losing recorded rides.
- **The cockpit does not yet match the HUD spec.** Section 5 of the design spec calls for
  a cruising state with speed plus distance-remaining plus ETA plus the current street
  name, a persistent recenter control, and the safety states (GPS-weak, off-route,
  permission-denied). What shipped is a clean stats card with speed, distance, time, and
  elevation, no ETA, no street name, no recenter, and none of the edge states. Off-route
  reroute is not observed at all, so after a reroute the rider would see the old line while
  being guided down a new one.
- **Strict concurrency is off.** Both modules build in Swift 5 language mode with no
  strict-concurrency flags, and CI leans on a newer toolchain downgrading data-race
  violations to warnings. The code is written to a high Swift 6 standard already, so the
  gap between how it is written and what the compiler checks is small and worth closing.
- **The app target is untested and unbuilt in CI.** All 102 tests live below the app
  boundary, in the pure package. CI runs `swift test` only and never compiles the app, so
  a break in a Mapbox provider, a view, or the wiring passes green. There is no SwiftLint
  config and no lint step. The Terrain-RGB elevation bug (compiled fine, returned flat
  everywhere) is the cautionary tale for why a clean build is not enough here.
- **There is no design system, only a color sheet.** `AuraTheme` is eight flat colors and
  two font helpers. Spacing, radii, elevation, and the type ramp are improvised per view
  (corner radii alone span seven values). The route green is a hardcoded RGB duplicated
  across four map files instead of flowing from the token. The taste is good; the system
  underneath it is missing.
- **Accessibility is strong on motion, weak in the cockpit.** Reduce Motion is honored
  everywhere and the Dynamic Type pass is real, but the SpeedRail and TurnCard, the two
  most important elements, have no composed VoiceOver labels, and the floating controls
  use thin material with no Reduce Transparency fallback and several borderline contrast
  values.

Full detail, including file and line references and severities, lives in the audit notes
that produced this section.

## Build order

The waves are ordered so that structural work lands before the features that depend on
it. Each wave is shippable on its own.

### Wave 0 — Make the core ride actually work

Correctness for the flagship behavior. Nothing else matters if a ride can lose its track.

- Add and sign an `Aura.entitlements` file with Background Modes (location), wired through
  `project.yml`. Keep the existing Info.plist `location` mode.
- Request When-In-Use first, then escalate to `requestAlwaysAuthorization()` when a ride
  starts, and handle the result in the authorization delegate.
- Set `isIdleTimerDisabled` while recording and reset it on end.
- Add the safety states the spec requires: a GPS-weak indicator driven by
  `horizontalAccuracy` and fix age, an off-route "Rerouting" cue wired to the Mapbox
  reroute publisher (and redraw the polyline from live progress, not the frozen geometry),
  and a permission-denied explainer with a deep link to `openSettingsURLString`.

### Wave 1 — Structural foundations

The rebuilds that make every later wave cheap and safe. Do these before feature work.

- **Navigation:** replace the `AppRouter.screen` switch with a `NavigationStack(path:)`
  over a typed `Route` enum and one `.navigationDestination`. Keep `AppRouter` as the
  `@MainActor @Observable` owner of the path and add a `handle(url:)` entry point for deep
  links. This also removes the per-transition Mapbox teardown.
- **Location service:** consolidate `LiveLocationProvider` and `CurrentLocationProvider`
  into one main-actor service that owns a single `CLLocationManager`, exposes an accuracy
  mode (idle vs navigating, the spec's battery strategy), publishes auth and signal
  quality, and vends both a one-shot origin and the live ride stream. Replace the
  `MainActor.assumeIsolated` bridge with an explicit hop.
- **Persistence:** drop `@Attribute(.unique)`, move `trackData` to
  `@Attribute(.externalStorage)`, denormalize the summary fields (distance, duration,
  elevation, name) into stored columns so the History list never decodes a track, and wrap
  the current model as `SchemaV1` with a `SchemaMigrationPlan` and a round-trip migration
  test.
- **Ride-session coordinator:** route ride start and finish through one `AuraKit`
  coordinator instead of duplicating the logic in both HUDs. This is the seam that Live
  Activity, HealthKit, and haptics will all hook into, and it makes ride completion
  testable.
- **Design system:** promote `AuraTheme` into color roles, a spacing scale, a radius
  scale, and a type ramp, with a `UIColor`/`StyleColor` bridge so the route polyline stops
  being a magic number in four files. Extract the repeated components (the aurora CTA, the
  stat pair, the HUD control button with a Reduce Transparency fallback).
- **Quality gates:** turn on strict concurrency in dependency order (AuraCore, then
  AuraKit, then the app), add an `xcodebuild build` job for the app to CI, and add
  SwiftLint with a committed config and a `--strict` CI step.

### Wave 2 — The cockpit the spec promised

With the foundations in place, build the HUD the design spec describes.

- Add distance-remaining, ETA, and the current street name to the navigate HUD (the data
  already flows through `GuidanceViewModel`).
- Add a recenter control and unify it with mute and end-ride into one control cluster
  built on the new HUD control component.
- Give the SpeedRail and TurnCard composed VoiceOver labels.
- Redesign the ride summary away from the orphaned stat stack into a balanced grid or a
  true hero metric, and lift the borderline contrast values across the app.

### Wave 3 — Near-term features

These were the old "Next steps." The Live Activity and Dynamic Island have since shipped
(see Shipped, above) — built straight from the ride HUDs ahead of the Wave 1 coordinator,
which left the `AuraWidgets` extension target and `NSSupportsLiveActivities` in place. The
rest become mostly additive once Wave 1 lands.

- HealthKit: write completed rides as cycling workouts at ride finish via `HKWorkoutBuilder`.
  Needs the HealthKit capability, the write usage description, and a thin testable
  `WorkoutWriter` seam. Smallest blast radius of the three.
- Haptics on turn approach and arrival, edge-triggered in the view model so they fire once
  on the false-to-true transition, gated by a settings toggle.
- A home and lock-screen widget for the last ride and weekly goal, reusing the
  `AuraWidgets` extension the Live Activity introduced. Timeline widgets that read saved
  rides will need an App Group (the Live Activity itself did not).

### Wave 4 and beyond — Platform and the group-ride future

- iCloud sync with CloudKit, now unblocked by the Wave 1 schema changes. Needs the iCloud
  capability, a CloudKit container, the remote-notifications background mode, and a
  development-to-production schema rollout.
- CarPlay, using the Mapbox v3 CarPlay templates and the existing `GuidanceSession`
  abstraction. Needs the CarPlay entitlement (Apple approval) and a scene delegate.
- Apple Watch companion.
- Group rides (Phase 2): a `RideSession` wrapping the existing `Ride`, with Supabase for
  auth, Postgres, and realtime live location. Re-research the realtime stack before design.
- Push-to-talk voice within a session (Phase 3), Strava export, and HR/power sensors.

### Smaller fixes

- Per-route elevation sparklines are normalized to their own min and max, so a flat route
  and a hilly one can look similar. A shared vertical scale across the visible options would
  make the comparison honest at a glance.
- Elevation gain is sampled at only 16 points per route, which undersamples climb on longer
  routes and weakens the "Flattest" ranking. Sample proportionally to distance.
- The Mapbox alternative-to-label correlation matches on exact `Double` distance equality,
  which can mis-map two equal-distance alternatives. Carry the Mapbox index through the
  candidate pipeline instead.
- `DestinationSearchView` keys its results `ForEach` on the array offset, which churns row
  identity as suggestions stream in. Use a stable key.

## Testing

The `AuraCore` package has 105 XCTest tests covering the pure layer: GPX parsing, stats and
ranking (including that "Most paths" avoids forced-walking routes), unit conversion, the
turn-card and guidance pipelines, the week-to-date aggregation, and the plotting math. The
gap is the app target: every SwiftUI view, every Mapbox-backed provider, and the
app-target location code are untested and not even compiled in CI.

Near-term testing work, sequenced with the waves above: build the app target in CI and add
SwiftLint (Wave 1), add the schema migration test alongside the persistence rebuild
(Wave 1), and adopt Swift Testing for new tests. UI work is still verified by running the
app on the simulator and checking the actual screens, since a clean build is not enough to
catch a feature that silently does nothing (the Terrain-RGB elevation switch is the
cautionary tale: the first implementation compiled fine and returned a flat value
everywhere).
